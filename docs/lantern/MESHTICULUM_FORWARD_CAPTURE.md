# Experimental MPF2 operation, receive journal and capture contract

**The protected receive journal, capture import, canonical receiver and five-stage operation/parent budget have experimental source and temporary encrypted-backend evidence.** Core recognizes an explicit MPF2 record shape, and Lantern now has a source-only stage adapter. Native owner/consent/Noise-purpose providers, five-stage native provisioning and private format/flow activation remain unqualified. The public bundle excludes private providers. Lantern owns protected storage, capture, consent and native lifecycle; Meshticulum owns generic crypto/flow interfaces. The dependency remains Lantern → Meshticulum.

MPF2 DATA replay acceptance must commit with an exact recoverable sealed record. Calling the current `ForwardSession.open(packet)` and then `BinaryCapture.complete(...)` does not meet that requirement.

## The current gap

At the historical [Core cf64d62](https://github.com/l33tdawg/meshticulum/blob/cf64d623abb707c342524fac951b88cf0a1e63e6/src/meshticulum/privacy/forward_session.py), `open()` authenticates the MPF2 record, checks the binary-envelope shape, commits its receive counter and then returns sealed LM1/LM2 bytes. Lantern's [BinaryCapture](../../software/meshticulum-integration/src/lantern_meshticulum/sage/mesh_binary_capture.py) separately persists those bytes with a [WorkflowStore](../../software/meshticulum-integration/src/lantern_meshticulum/sage/workflow_store.py) compare-and-swap.

A crash or failed capture between those operations can leave a durable accepted counter with no captured bytes. Replaying the network record is refused, and persisting only the MPF2 ciphertext is insufficient when the non-resumable session keys are gone. Separate durable writes, or a second callback that runs after `open()`, do not remove this gap. This return-then-capture pipeline must remain unwired for the private mode.

## Implemented generic receive seam

The generic receive seam introduced at [Core 30da536](https://github.com/l33tdawg/meshticulum/blob/30da5360961b17fd50a8ba304d6bc82e58c8ca26/src/meshticulum/privacy/forward_session.py) supplies constructor `receive_mode='commit'`, `receive_into(packet)` and a frozen `ReceiveCandidate`; current [Core 4fa367](https://github.com/l33tdawg/meshticulum/commit/4fa367) also provides the explicit record-format boundary below. Paired dependencies and source locks must match the candidate being tested. Commit mode requires a callable `counters.commit_receive` before any claim and refuses `open()`. Default return mode refuses `receive_into()`. The mode is a local choice, without peer capability negotiation or storage attestation.

After full confirmation, authenticated DATA, binary shape and original liveness checks, Core passes the candidate to that same counter provider. It contains context, local role, original counter binding/counter, transcript and outer hash, original monotonic deadline, observation times and sealed bytes hidden in its representation. Only literal `True` followed by successful liveness checks returns success, without returning payload. DATA uses no separate `record_receive`; confirmations retain that path. Unknown outcomes, closing callbacks or interruption fence the incarnation while a possibly committed capsule remains the provider's recovery responsibility.

Core does not attest the callback's atomicity or native permission. A constructible candidate is not a bearer authorization; it does not supply a capture UUID, boot identity or private policy. The Lantern provider must independently bind those facts to the original prepared intention. The experimental Lantern journal consumes this seam in source and backend fixtures. No native private provider or format activation is wired to it.

### Generic MPF2 format recognition

Core 4fa367 adds the explicit `MPF2.record` service format for generic radio/IP composition. Its inspector checks bounded MPF2 framing and record shape; endpoint authentication, handshake phase, native permission and application admission remain external. Nineteen focused format controls pass. The exact Core standalone candidate passes 1,704 with five expected skips on each Python 3.11–3.13 CI job ([run 38072704998](https://github.com/l33tdawg/meshticulum/actions/runs/38072704998), [run 38072702068](https://github.com/l33tdawg/meshticulum/actions/runs/38072702068)); those runs produced no retained artifacts. These are source results, not native private activation.

The existing Lantern `LME.binary` private runner still refuses MPF2 with `forward_runner_requires_stage_adapter`. The dedicated experimental stage adapter and durable aggregate budget are described below; they do not make that legacy runner compatible. Independent reverse grants and a qualified five-stage native provisioner remain required. Recognizing a format or constructing a generic transfer cannot enable native private dispatch.

## Implemented protected journal

[ForwardReceiveJournal](../../software/meshticulum-integration/src/lantern_meshticulum/sage/forward_receive_journal.py) uses one recipient-signed `mesh_inbound` WorkflowStore record. Its stable claim ID depends only on the existing session-ID/local-role counter binding; changing context, mode, operation UUID or dedicated key pins cannot evade a retained claim. Creation is the journal's sole original receive preparation, before handshake/flow. It persists the owner-supplied operation UUID, expected sealed length/digest, authority binding, boot and original epoch/monotonic deadlines with preparation observations.

That same record owns transmit reservations, confirmation replay counter 1 and one expected DATA counter 2. Capsule presence is DATA acceptance. Exact sealed bytes, full context, transcript, outer digest and observation times enter the same signed CAS; there is no later DATA replay write or capture RPC. Conflicting/unknown writes fence the producer and retain committed state. The provider allows one expected DATA per original intention/session and does not rotate sessions, renew deadlines, refund counters or clear prior transport debt.

Live instances remember their highest validated/confirmed revision and canonical body. Older signed rows or different signed content at the same revision fence that incarnation. This does not prove protection against database restoration after a fresh process starts. Claims and capsules are retained; deletion, backend restoration and eventual final disposition remain separate review gates.

The native caller supplies the exclusive lease and current access/storage/peer/dispatch permission guards. This new interface requires permission observations both inside the lease and after exit; ownership and current permission are independent checks. A callback that requires a held lease will fail closed after exit and is not automatically compatible. Storage/time observations finish before the final permission guard, so callbacks cannot revoke read permission and still publish a stale result. No production native provider has been qualified against this contract.

A fresh authorized instance can read the signed quarantine through `recover()` without old session keys. It preserves the original preparation, observation, UUID, descriptor and deadlines. Permitted historical reads can occur after original expiry or boot change; they grant no fresh dispatch or application admission. `ReceiveRecovery` is a constructible data object, not bearer authority, signed import evidence or a native attestation. The capture importer therefore reads and verifies the actual protected journal instead of accepting that object or caller-provided bytes.

## Implemented capture import

[`BinaryCapture.import_forward`](../../software/meshticulum-integration/src/lantern_meshticulum/sage/mesh_binary_capture.py) requires a fresh, unclaimed `ForwardReceiveJournal` validator with the exact same WorkflowStore, local recipient/signing identity, current boot and lease factory as the capture owner. One shared lease protects the operation; the validator does not acquire a second lease. Both objects stay busy through final observations and permission guards, fencing closing or caught reentrant callbacks. Current read-permission checks must work inside the lease and after exit.

Import performs an actual protected GET, verifies the recipient's journal signature, context, intention and committed capsule, and checks current storage/peer/read permission. It accepts neither a `ReceiveRecovery` object nor a caller-supplied packet. The journal remains the sole authoritative original intention created before handshake/flow. Import does not call `BinaryCapture.prepare()` or stamp a new preparation.

The capture preserves the original operation UUID, sender, sealed-object length/digest, authority, epoch/monotonic deadlines and original boot. It also retains original preparation and observation times: epoch preparation/capture fields and monotonic provenance fields come from the signed source. Historical quarantine can be imported after expiry or a boot change when current protected reads are permitted. A separate `process_pending()` first reconciles an existing signed inbox admission; otherwise it rejects expired or changed-boot work instead of creating fresh admission. Import alone does not open the inner envelope, project a private message or issue a delivery/read receipt.

Every replay import re-reads the actual signed source. Capture provenance retains the original journal revision/body hash, context/transcript/outer hashes and original intention, plus the latest observed source revision/body hash. A legitimate transmit-counter advance may update that monotonic observation while preserving the original import proof and immutable capsule facts. Older source rows or same-revision hash changes are refused against the retained observation. This does not prove resistance to restoration of both protected records or a native rollback attack.

Successful processing carries that provenance into `last_completed`; acknowledgement clears the retained capture payload while preserving the signed provenance/tombstone. Re-importing the same settled operation does not resurrect it. An unrelated outstanding intention cannot be replaced. Import uncertainty or later admission uncertainty retains the authoritative source for explicit recovery under the original UUID. **The forward journal is never cleared by import, processing or acknowledgement.**

## Canonical receiver composition

[`ForwardReceiver`](../../software/meshticulum-integration/src/lantern_meshticulum/sage/forward_receiver.py) composes the canonical `lantern_meshticulum.sage` MessageStorageProbe, WorkflowStore, ForwardReceiveJournal, BinaryCapture and MeshInbox around an already owned, borrowed SDK client. It does not substitute similarly named runtime classes or loose provider objects. It creates no new client, radio, listener, identity or grant. The original context/intention, recipient signing identity, endpoint, current boot and one owner lease remain explicit inputs.

The native caller must supply current access, storage, peer, original-context dispatch, protected-read and dedicated-Noise-purpose observers, plus its clock and shared lease. Crypto authorization checks the pinned local Noise public key's purpose and its context binding. These mandatory callbacks do not establish enrollment, independent key generation or native authority merely by returning `True`. Current read rights are checked on every protected dispatch, settlement and acknowledgement/clear, not only historical import; observers must remain valid inside and after lease exit.

`create_session()` permits one commit-mode incarnation and uses the canonical journal as its counter/receive provider. `import_pending()` constructs a fresh unclaimed validator and performs the signed import. `settle()` and `acknowledge()` retain the original operation and independent inbox boundary. Historical import/reconciliation requires current protected reads, without requiring a retired Noise key or fresh dispatch permission; it grants neither session reuse nor expired admission.

Composition/child guards fence cross-entry during active crypto and caught callback reentry. SDK identity, endpoint, transport, signing-key or closed-client drift is rejected at crypto boundaries, including handshake stages that perform no storage write. `close()` cannot certify a clean join while a child operation is active or from a wrong-process copy. It fences owned crypto/journal/capture state while leaving the borrowed client/store, retained claims, capsules and original debt intact. This is source ownership enforcement, not proof of a production owner or physical quiescence.

## Experimental five-stage operation and parent budget

[`ForwardOperation` and `ForwardStageRunner`](../../software/meshticulum-integration/src/lantern_meshticulum/sage/forward_operation.py) coordinate one fixed-context MPF2 exchange using exact `ServiceTransfer` instances with `format='MPF2.record'`. The original `ForwardContext` and inner `ReceiveIntention` bind the session, peers, expected sealed descriptor, operation UUID, authority, epoch expiry, host monotonic deadline and boot. Each immutable child plan adds an explicit record kind, local send/receive direction, ordered slot, grant/profile digest, packet descriptor and enforced transport caps. A child may tighten the original monotonic deadline; it cannot renew it or change the original epoch expiry/boot.

| Stage | MPF2 record | Logical direction |
| --- | --- | --- |
| 1 | `H1` | Initiator → responder |
| 2 | `H2` | Responder → initiator |
| 3 | `CONFIRM_I` | Initiator → responder |
| 4 | `CONFIRM_R` | Responder → initiator |
| 5 | `DATA` | Initiator → responder |

The operation checks the exact session ID, kind/counter, original liveness and current native/crypto permission at each stage. Receive crypto requires the matching completed transfer and descriptor; a caller cannot advance it by supplying an arbitrary packet. Cached outbound records support carrier retries inside the live exchange, without creating another crypto incarnation. The implementation provides no automatic grant/context rollover or resumption policy. Unknown ownership or stage outcomes fence the operation.

[`ForwardBudget`](../../software/meshticulum-integration/src/lantern_meshticulum/sage/forward_budget.py) retains a signed protected WorkflowStore CAS record under the actor/original-operation identity. Its binding includes the original context/intention, aggregate limits, prior debt and ordered kind/direction slots. `pre_admit()` prepays the **full enforced child maxima**: radio `AttemptJournal` attempts and estimated airtime, or IP grant frames and both TX/RX stream bytes. The runner re-reads those actual caps through `describe_child()` and checks the exact child binding, including cipher frame limit. Each grant digest/slot is single-use; changing a grant, descriptor, context or limits cannot erase an existing allocation or prior debt.

`prepare_stage()` commits that allocation before invoking the trusted `open_child` factory, so failed/uncertain pre-admission cannot open a socket or ARM a radio child. An exact unbound permit, protected allocation and current storage epoch are rechecked after operation callbacks and immediately before factory entry; callbacks remain inside the budget reentry fence. The stage also retains cipher/grant identity through its pre-dispatch checks. Construction, cancellation, partial use and a lost CAS return give no refund. A fresh owner may observe the retained allocation as debt, but cannot reconstruct its instance-owned `Admission` handle or replay the spent slot. Native prior-debt observations, physical limits and fresh-process/backend-restoration protection remain qualification work; a signed budget or `True` callback is not dispatch authority.

The stage loop holds the shared owner lease for transport and terminal retirement. It releases native/application transport leases before endpoint crypto, journal and later capture work; protected storage uses its own guarded acquisition of that same lease, without nesting it beneath transport. Wire completion does not advance the stage. An explicit retirement callback must finish the bounded late-ACK window, disarm/join the child and report terminal retirement before the operation advances. TCP receive retirement first finishes its receive ACK. The radio retirement/airtime checks remain modeled; local loopback TCP tests exercise actual kernel transport and flow ACK behavior. Neither proves physical radio quiescence or native policy.

## Experimental Noise purpose and retirement

[`NoisePurpose`](../../software/meshticulum-integration/src/lantern_meshticulum/sage/noise_purpose.py) reserves a stable actor/original-operation namespace before independently generating one X25519 key in RAM. Signed protected CAS records contain public purpose, pin, original intention/context, observations and retirement metadata. Any existing reservation, bound record or tombstone prevents replacement generation under that operation; changing role, generation ID, approval, boot or lifetime cannot create a fresh namespace. There is no private-key export, persistence, import or fresh-process key recovery API.

Binding requires separate current local enrollment and remote-pin consent. Exact context object/digest/canonical metadata stay bound through callbacks. Purpose observers perform protected reads without acquiring the setup lease; their independent access/consent callbacks must not recurse through the native owner that calls them. A one-use handle hands the key to a fresh session/operation factory. Mandatory abort cleanup is registered before handoff, closes retained or unreturned factory resources after factory exit and must return literal `True`; failed cleanup remains uncertain.

Retirement fences the key and registered sessions, including their post-split traffic keys, before attempting the signed public tombstone. A lost return leaves the owner uncertain even if retirement committed. Existing claims, counters, original intentions and parent debt remain retained. Local `close()` is cancellation rather than a durable retirement receipt. These contracts provide no automatic regeneration/resumption, fresh-process restoration resistance or forensic zeroization proof; native key custody/enrollment and physical retirement remain unqualified.

## Source-only native owner composition

[`ForwardNativeOwner`](../../software/meshticulum-integration/src/lantern_meshticulum/sage/forward_native_owner.py) borrows an exact existing `HardwareRuntime`, identity and SDK client. It does not call `provider()` or open a radio. The original authenticated root request must grant four independent live scopes—`meshticulum_forward_read`, `meshticulum_forward_receive`, `meshticulum_forward_dispatch` and `meshticulum_forward_control`—against the exact approval digest binding the original context/intention, local role, configuration revision, broker and storage epoch. An old receive grant or unlocked state cannot substitute for those permissions.

Current observations pin resource/client/signing references, configuration, broker, storage/access epochs, boot and original lifetime, with separate local and remote dedicated-Noise-purpose callbacks. The shared hardware mutex and checked `CaptureLease` enclose protected work; current permission observations run before acquisition, inside the lease, after work and after lease exit. A retained drain lease is not fresh permission. `operation()` prepares the parent, then uses `BinaryCapture.state()` to observe the actual signed shared capture as idle before creating crypto. An unrelated non-idle capture refuses construction; an unseen capture remains conservative for closure. Both roles use canonical durable journals with the same budget store/intention/lease, derived stage directions and omitted initiator settlement. Tracked composition/session/counter/budget bindings are rechecked through observation callbacks. Construction, active work, wrong-owner access or an unobserved capture prevent a clean-close result.

This owner requires live original permissions, boot and deadlines even for reads; historical recovery after expiry or boot change is excluded from this composition. The earlier [native-owner fixture suite](../../software/meshticulum-integration/tests/integrations/sage/test_forward_native_owner.py) passed 33 controls before the child-tracking increment, including all five stages with actual MPF2 crypto/canonical journals and modeled radio, SDK backend and native inputs. Native transport provisioning, activation and owner/enrollment qualification remain open.

### Child tracking and shutdown containment

[`ForwardChildren`](../../software/meshticulum-integration/src/lantern_meshticulum/sage/forward_children.py) registers cleanup ownership after protected prepayment and before the factory can open/ARM a child. Exact runner/transfer bindings and independent containment/terminal callbacks remain required. A shared unknown latch fences the resource's owners when construction or terminal observations fail; successful containment does not erase that uncertainty or prepaid debt.

Shutdown fences new work, waits for active factories, callbacks, crypto and protected writes to unwind, and drains children outside the hardware mutex. Only the registry's same-PID, quiescent one-use close permit can delegate logical component closure to its drain thread; public wrong-thread close semantics remain unchanged. Normal retirement uses original live authority for the bounded late-ACK path. Shutdown containment grants no fresh ACK/application dispatch and requires its own terminal observation. Source callback/barrier checks do not establish physical quiescence or qualified native shutdown.

### Known lease refusal and supervisor restart

The existing native receive path now distinguishes an observed refusal before a fresh lease token is returned using the narrow [`MeshLeaseRefused`](../../software/runtime/src/sage_lantern/mesh_community.py) type. The trusted local factory emits it only at that no-acquisition boundary, and `MeshActionAuthority.receive_grant()` preserves it. Other acquisition failures, including a lost issued-token return, and lease-close errors remain uncertain. The signal grants no permission, proves no retirement and cannot be inferred from exception text, an empty journal or a missing process. Unresolved `receiving` records still block clean closure.

Background restart remains owned by the [hardware supervisor](../../software/runtime/src/sage_lantern/mesh_daemon.py). Requests check readiness/current authorization and never resume a paused worker. [Controlled supervisor-tick tests](../../software/runtime/tests/test_mesh_daemon.py) replace the stale expectation that an immediate `ready` request restarts it, and verify refusal under lost ownership or uncertainty.

## Required protected transaction

The generic seam makes the authenticated sealed candidate available **before** the provider commits DATA acceptance. A production adapter must preserve callback fencing, original authority/deadlines and dedicated-key bindings. It must not expose decrypted application content or let callers bypass key confirmation. Core must not import Lantern or SAGE.

The Lantern adapter must join the following in one authoritative, protected, durable receive transaction:

- A create-only replay entry for the existing session-ID/local-role namespace and DATA counter. Changing context or mode must not evade an existing claim.
- The exact sealed LM1/LM2 bytes, their length/digest, the authenticated outer-record digest and the full context/transcript/peer binding needed to verify the recovery record.
- The original prepared capture operation UUID, expected sealed-object descriptor, authority binding, boot identity, epoch expiry, monotonic deadline and trusted observation metadata.
- A bounded pending disposition and authenticated commit receipt. A conflicting record under the same receive identity must fence the producer rather than overwrite it.

Every committed DATA replay entry must therefore identify recoverable sealed bytes or a durable final disposition. An entry that claims acceptance while its required capture/recovery record is missing is an integrity failure, not a retry opportunity. The transaction must validate the original intention and current native storage/owner/consent guards; uncertain or expired operations cannot publish success.

This can be a single backend transaction or one bounded protected record updated atomically. A local replay SQLite transaction and an independent REST capture CAS are two commit boundaries. SQLite atomicity covers changes inside its transaction; WAL does not make transactions across separate attached databases collectively atomic. Neither mechanism joins an unrelated backend RPC. [SQLite atomic commit](https://www.sqlite.org/atomiccommit.html), [WAL constraints](https://www.sqlite.org/wal.html)

The receive journal acts as the recoverable source for the later capture import. That import is a separate CAS under the original UUID and descriptor; its failure cannot remove the authoritative accepted sealed bytes. The signed journal and capture provenance establish quarantine, without claiming inner-envelope admission or SAGE delivery. No ephemeral or traffic-key persistence is required to recover already committed sealed bytes; authenticated protected reads and the recipient identity remain required.

## Recovery and admission

| Failure boundary | Required result |
| --- | --- |
| Before the joint receive commit | No accepted DATA marker or recovery capsule. Preserve the original unresolved intention and prior transport cost; this document grants no fresh dispatch. |
| Joint commit succeeds but its return is lost, or a later guard/lease exit closes the producer | Fence the producer. A fresh authorized owner probes the exact receive identity and original operation, verifies the protected receipt/bytes, and reconciles; it does not reset the counter or create a new UUID. |
| Capture import fails or has an unknown return | Keep the joint recovery record. A fresh unclaimed validator re-reads the actual signed source and capture state; retry only the matching original import when current reads are permitted. |
| Inbox admission commits but its return/clear is lost | Probe the existing recipient-signed inbox admission and retain its disposition before clearing payload state, using the existing explicit reconciliation boundary. |
| Original authority expires, boot changes or consent is unavailable | No fresh admission. Current permitted reads may reconcile an existing signed admission or record an authorized rejection; otherwise retain the pending record and refuse. |

After protected capture, [MeshInbox](../../software/meshticulum-integration/src/lantern_meshticulum/sage/mesh_inbox.py) must independently open the inner envelope with pinned peers, verify its signature, enforce expiry/replay/consent and create or reconcile the locally signed inbox admission. Captured bytes, a cryptographic receipt, a flow ACK, inbox admission and canonical SAGE commit are distinct outcomes. Application receipts must not precede their corresponding durable admission. Explicit payload clearance must preserve required replay claims, tombstones and prior attempt/airtime/stream-byte debt.
